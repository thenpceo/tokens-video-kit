## Vision

### 10x Check

The best version is not a generic news monitor. It is a postability engine for Tokens: a system that knows which sources produce fast, valuable, post-worthy market news; explains why an item is or is not P0; learns from Nicholas's Slack feedback; and improves source priority over time.

The felt experience should be: Slack is no longer a feed to babysit. It is a trusted editorial queue. If an item lands in `P0_POST_NOW`, the team should expect it is sourced, fresh, relevant, non-duplicate, draftable, and likely worth posting.

### Current To Ideal

```text
CURRENT STATE
  Strong editorial analysis and source registry, but no running feedback loop.

THIS PLAN
  Build a Tokens-specific postability engine with ingestion, hard gates, Slack decisions,
  human ratings, missed-story review, source health, and copy learning.

12-MONTH IDEAL
  A self-improving market-news editor that ranks sources by real posting outcomes,
  catches misses, reduces rewrite time, and makes every alert explainable.
```

## Accepted Scope

- Standalone Tokens-specific postability engine using the source registry as configuration.
- Registry-driven ingestion across X, RSS/IR/company sources, SEC, macro sources, Solana/RWA ecosystem sources, and detector-only accounts.
- Candidate event normalization, URL expansion, entity resolution, hard gates, editorial scoring, clustering, dedupe, and draft generation.
- Slack queues: `P0_POST_NOW`, `P1_VERIFY`, `P2_ROUNDUP`, and `MONITORING`.
- Slack feedback buttons: `Post-worthy`, `Useful`, `Who cares`, `Duplicate`, `Stale`, `Bad source`, `Wrong fit`, `Add note`.
- Rolling source quality scores based on human ratings, post outcomes, stale rate, duplicate rate, source trust, and missed-story backtraces.
- Missed-story review command/form that backtraces why a high-value story was not surfaced.
- Human-in-the-loop copy learning from draft to approved/posted copy.
- Structured "Why this is not P0" reason codes for all non-P0 candidates.
- Source health monitoring for dead feeds, auth failures, rate limits, malformed responses, stale polling, and source quiet periods.

## Deferred To TODO

## Product Requirements

- `P0_POST_NOW` must remain the measured queue for the 98% Slack-to-X postability target.
- Non-P0 queues are allowed to be noisy enough for discovery, but every item needs a reason code.
- Human feedback is first-class data, not an annotation afterthought.
- The system must distinguish "bad source", "wrong fit", "who cares", "duplicate", and "stale" because each implies a different source-priority adjustment.
- Source health state must be separated from source quality. A high-quality source that is temporarily broken should not be demoted as editorially bad.

## Acceptance Criteria

The 98% target is measured only on the `P0_POST_NOW` queue.

Definition:
- Numerator: P0 candidates marked `Post-worthy`, `Approved`, or `Posted`.
- Denominator: all P0 candidates sent to Slack, excluding exact duplicates already attached to an active cluster.
- Review window: rolling 7 days and rolling 30 days.
- Minimum sample size before declaring success: 50 P0 candidates.
- Postable means: a human reviewer would be comfortable posting it after, at most, light wording edits. It must have a credible source, clear asset/thesis link, non-stale timing, non-duplicate event, and enough factual detail to draft.

Operational targets:
- Median source publish to Slack P0 latency: under 15 minutes for X/official/RSS sources, under 20 minutes for SEC/macro sources.
- P0 false-positive rate: under 2% once the sample size threshold is met.
- Every non-P0 candidate has at least one automated routing reason.
- Every source has separate quality and health states.
- Every candidate has a decision trace sufficient to debug why it did or did not reach P0.

## Connector Requirements

V1 connector order:
1. RSS/company/IR/project feeds from `config/source-registry.json`.
2. SEC company filings RSS/API for mapped CIKs.
3. Slack posting and interactive actions.
4. X ingestion if `X_BEARER_TOKEN` and usable API access are configured.
5. Macro/government pages as polling sources.
6. Detector-only X accounts only after the trace model works for primary sources.

Connector behavior:
- Each connector writes `raw_ingest_event` before transformation.
- Each connector records `source_id`, `source_type`, `fetched_at`, `published_at` when available, HTTP status, response hash, and parse status.
- Network calls use bounded timeout, retry with exponential backoff, and per-source rate-limit state.
- Parse failures become source-health events, not silent drops.
- X URL expansion and thread/quote context are best-effort in v1; missing context forces `P1_VERIFY` or lower.
- SEC and macro official sources may enter P0 if the entity and draftability gates pass.

Degraded mode without X API:
- V1 is still valid if RSS/company/IR/project feeds, SEC, Slack, and registry replay work.
- X-only sources remain in the registry but are marked inactive until `X_BEARER_TOKEN` and API permissions are configured.
- Validation in degraded mode requires at least 20 source-generated candidates from non-X sources and successful Slack routing/feedback.
- The system must clearly report `x_ingestion_disabled` in source health, not silently ignore X sources.

## Source Scoring Model

Each source gets rolling scores by window: 24h, 7d, 30d.

Inputs:
- `post_worthy_count`
- `useful_count`
- `who_cares_count`
- `duplicate_count`
- `stale_count`
- `bad_source_count`
- `wrong_fit_count`
- `posted_count`
- `missed_story_count`
- `p0_candidate_count`
- `p1_candidate_count`
- median source-to-Slack latency
- confirmation rate for Tier B/C detectors

Source health is tracked separately:
- `last_success_at`
- `last_error_at`
- consecutive failures
- last HTTP status or connector error
- stale polling flag
- rate-limit flag
- parse failure rate

Default priority adjustment:
- Boost: `Post-worthy`, posted outcome, low latency, high confirmation rate.
- Mild boost: `Useful`, especially if later used in roundup or source confirmation.
- Demote relevance: `Who cares`, `Wrong fit`.
- Demote trust: `Bad source`, repeated unconfirmed detector claims.
- Demote routing only: `Duplicate`, `Stale`.
- Do not demote editorial quality for source health failures; alert separately.

Learning means three concrete things in v1:
- Source priority updates: rolling quality score changes future polling and routing priority.
- Rule feedback: repeated labels such as `Who cares` or `Wrong fit` attach to asset/topic/source patterns for review.
- Copy examples: final posted copy is stored next to draft copy for later template/prompt tuning.

V1 does not auto-adjust source tiers without a review record. It can recommend demotions/promotions, but Tier A/B/C changes remain explicit config edits.

V1 source quality formula:
- `positive = post_worthy_count * 3 + posted_count * 3 + useful_count`
- `negative = who_cares_count * 2 + wrong_fit_count * 2 + bad_source_count * 3 + stale_count + duplicate_count`
- `quality_score = clamp(50 + positive * 5 - negative * 5 + confirmation_bonus + latency_bonus, 0, 100)`
- `confirmation_bonus = 10` when a Tier B/C detector confirms into primary source at least 60% of the time over the window.
- `latency_bonus = 5` when median source-to-Slack latency is inside target for the source type.

Thresholds:
- fewer than 10 rated candidates in a window: `insufficient_data`.
- score 75+: recommend priority boost.
- score 45-74: maintain priority.
- score below 45: recommend demotion.
- score below 30 with at least 20 rated candidates: recommend route downgrade or removal review.

## Gates, Scoring, And Queue Routing

Hard gates:
- `trusted_source`: Tier A source, or Tier B/C source with confirmation.
- `fresh`: inside category TTL from source published time or first seen time.
- `relevant`: direct asset, indirect tradable exposure, macro basket, or platform-thesis match.
- `verified`: official/primary source or two trusted independent sources for rumor-like claims.
- `non_duplicate`: no active cluster already covers the same event.
- `draftable`: enough facts to write a Tokens-style post without guessing.

Editorial score:
- Asset relevance: 0-3.
- Market movement potential: 0-2.
- Specificity/data: 0-2.
- Timeliness: 0-1.
- Platform thesis fit: 0-2.

Routing:
- `P0_POST_NOW`: all hard gates pass and editorial score is 8-10.
- `P1_VERIFY`: strong relevance but missing confirmation, thread context, source detail, or exact draftability.
- `P2_ROUNDUP`: relevant but stale, non-urgent, evergreen, or score 6-7 without immediate catalyst.
- `MONITORING`: interesting source or topic but no clear Tokens post yet.
- `REJECTED`: wrong fit, bad source, failed ambiguity rule, or no asset/thesis path.

Automated non-P0 reasons and human feedback labels are separate. `who_cares` starts as human feedback unless a source/topic pattern has repeatedly received that label and is explicitly configured as low-value.

Registry route to engine queue mapping:
- `p0_eligible`: source is allowed to reach `P0_POST_NOW` only after all gates and score threshold pass.
- `p0_eligible_if_verified`: source can reach `P0_POST_NOW` only after confirmation/verification gate passes.
- `p0_eligible_if_official_or_trusted`: source can reach `P0_POST_NOW` only when the triggering source is Tier A official/primary or Tier B trusted and the verification gate passes.
- `p1_verify`: default engine queue is `P1_VERIFY` unless another primary source confirms the same cluster.
- `monitoring`: default engine queue is `MONITORING`; never P0 without explicit config override.

TTL table:
- breaking macro/geopolitical/rates: 15 minutes for P0, then `P2_ROUNDUP`.
- SEC 8-K/S-1/F-1/424B/material filing: 60 minutes for P0 if material and draftable, then `P2_ROUNDUP`.
- official company/product/partnership launch: 45 minutes for P0, then `P2_ROUNDUP`.
- tokenized market-structure launch/integration: 180 minutes for P0, then `P2_ROUNDUP`.
- onchain/RWA metric milestone: 6 hours for P0 if numeric and novel, then `P2_ROUNDUP`.
- generic commentary or analysis: never P0 unless it contains a new quantified fact from a trusted source.

## Slack Decision Surface

Each Slack card must include:
- headline
- queue priority
- source name, type, tier, URL, published time, first seen time, age
- matched assets and match type
- hard gate results
- editorial score breakdown
- reason code if non-P0
- draft copy
- risk notes
- feedback buttons
- action buttons: approve, needs source, rewrite, skip, mark posted

Slack action behavior:
- Actions are idempotent by `candidate_id`, `cluster_id`, `slack_message_ts`, `action_id`, and `user_id`.
- Multiple users may rate the same item; the latest rating per user is preserved, and aggregate rating drives scoring.
- `Approve` moves the candidate to `approved` and records reviewer/user/time.
- `Mark posted` requires an X URL or post ID before closing the loop as `posted`.
- `Rewrite` stores the requested edit reason and keeps the candidate in review.
- `Needs source` moves/keeps the candidate in `P1_VERIFY` and creates a source-gap trace.
- `Skip` requires or prompts for one of the feedback labels.
- `Add note` opens a note modal or records a threaded reply fallback if modal support is unavailable.
- Slack retries must not duplicate votes or state transitions.

## Persistence And Concurrency

SQLite is acceptable for v1 if writes are serialized through the worker process.

Requirements:
- unique indexes on canonical source URL, candidate cluster key, Slack action idempotency key, and posted X URL.
- explicit job leases for scheduled ingestion so overlapping runs do not double-post Slack cards.
- retry attempts and backoff stored per source.
- failed connector runs create source-health rows.
- all timestamps stored in UTC.

If multiple worker processes are needed later, move to Postgres before scaling beyond one writer.

Production storage:
- host: Render web service.
- database file: `/var/data/tokens-postability.sqlite` on a persistent disk mounted at `/var/data`.
- backups: daily SQLite backup copied to a second path on the disk; external backup can be added after the pilot proves value.
- startup must run migrations before the scheduler begins ingestion.
- shutdown must stop accepting Slack callbacks, release active job leases, and close SQLite cleanly.

Core tables:
- `raw_ingest_events`
- `normalized_candidates`
- `event_clusters`
- `decision_traces`
- `slack_messages`
- `slack_actions`
- `feedback_votes`
- `source_scores`
- `source_health_events`
- `copy_examples`
- `missed_story_reviews`
- `job_leases`
- `posted_links`

Phase 1: Primary-source ingestion and trace spine
- implement RSS/company/project feed ingestion, SEC feed/API ingestion, normalized candidates, clusters, decision traces, and basic routing without Slack actions.
- success: fixture/replay plus live primary sources produce traceable candidates.

Phase 2: Slack queues and feedback
- implement Slack message rendering, action signature verification, idempotent actions, feedback buttons, notes, and state transitions.
- success: candidates can be rated, approved, skipped, and marked posted without duplicate actions.

Phase 3: Source scoring and non-P0 explanations
- implement rolling source scores, route mapping, TTL table, reason codes, and source health alerting.
- success: every non-P0 item has a reason and every source has quality/health state.

Phase 4: Missed-story review and copy learning
- implement missed-story submission/backtrace and copy example storage/comparison.
- success: a pasted missed URL can be traced to a likely source/rule/gate failure; posted copy links back to draft.

Phase 5: X and detector sources
- enable X ingestion only if credentials and API access exist; otherwise keep degraded mode explicit.
- success: X candidates never silently disappear and detector-only items route to verify/monitoring unless confirmed.

## Implementation Direction

Recommended approach remains the Postability Engine, not a minimal shadow scorer or a full intelligence command center.

The implementation should be a standalone TypeScript/Node worker with:
- scheduled ingestion
- Slack action server
- SQLite persistence
- Zod validation
- Vitest tests
- no multi-client abstraction

Bootstrap checklist:
- initialize Node package and lockfile.
- add `src/worker.ts` for scheduled ingestion.
- add `src/server.ts` for Slack HTTP callbacks.
- add `src/config/env.ts` for environment validation.
- add `src/db/migrate.ts` and SQL migrations.
- add `src/registry/loadSourceRegistry.ts`.
- add fixture-based tests for registry, routing, dedupe, Slack action idempotency, and scoring.

V1 runtime:
- one long-running Node process can run the scheduler and Slack HTTP server together.
- scheduler uses job leases to avoid overlapping ingestion.
- Slack callback server must be reachable from Slack through a public URL in production or a tunnel during local testing.
- SQLite remains single-writer; all state mutations go through the same process.
- production target is Render web service with persistent disk at `/var/data`.
- service health endpoint: `GET /healthz` returns scheduler state, database connectivity, Slack signing config presence, registry load status, and degraded connector flags.
- readiness endpoint: `GET /readyz` returns unhealthy until migrations are current and the source registry is valid.
- deploy-ready pilot requires a successful migration, valid registry load, at least one successful non-X ingestion run, Slack callback verification, and one end-to-end feedback action recorded in SQLite.

Render environment variables:
- `NODE_ENV=production`
- `PORT`
- `DATABASE_URL=file:/var/data/tokens-postability.sqlite`
- `SOURCE_REGISTRY_PATH=/opt/render/project/src/config/source-registry.json`
- `SLACK_BOT_TOKEN`
- `SLACK_SIGNING_SECRET`
- `SLACK_POST_CHANNEL_ID`
- `SLACK_VERIFY_CHANNEL_ID`
- `PUBLIC_BASE_URL`
- `SEC_USER_AGENT`
- `X_BEARER_TOKEN` optional; absence enables explicit `x_ingestion_disabled` degraded mode.

V1 reporting surface:
- internal tables and CLI/report commands are in scope.
- polished client-facing digest is deferred.
- source score summaries are internal and operational, not client-ready reporting.
